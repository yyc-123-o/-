# 资源生成 Agent 当前进度与仓库初始状态对比

> 更新时间：2026-08-13
> 模块定位：CNN 个性化资源生成 Agent（候选学习包阶段）

## 一句话结论

刚拉下仓库时，项目已经具备“课程图谱、知识库治理、学情适配和资源生成契约”的底座，但资源生成仍主要是**确定性样例/候选草稿流程**；目前已补齐为一条可接真实兼容模型的受控生成链路：基于课程边界、冻结证据和学习者画像生成四类教学资源，并经过结构、证据、题答、Notebook 和发布门禁审核后，导出可展示的 CNN 候选学习包。

当前 CNN Demo 的真实发布状态固定为：`candidate_draft`。原因不是生成失败，而是“图像张量”前置知识尚未解除，且证据尚未达到 `approved` 正式发布状态。

## 一、刚拉下仓库时有什么

仓库原有能力主要集中在“上游治理与基础设施”：

- 课程知识图谱、概念前置关系、章节结构与深度分层；
- 学情画像适配契约与课程规划能力；
- 知识来源、证据块、引用与人工审核的治理模型；
- PostgreSQL、Qdrant、Neo4j 等存储对接框架；
- `ResourceBrief`、`EvidenceBundle` 等资源生成输入契约；
- 面向验收测试的确定性/假资源生成器；
- 候选证据覆盖分析与“未审核证据不得发布”的约束。

也就是说，原项目已经能回答“课程中有什么知识、学习者需要学什么、哪些资料可以进入候选库”，但还没有形成一套完整的、可以直接展示的资源生成闭环：**真实模型写内容、系统审核内容、系统执行 Notebook、展示个性化差异、并保证模型无法自行发布。**

## 二、当前已完成的工作

### 1. 建立受控生成契约与状态机

已实现并冻结以下核心对象：

- `ResourceGenerationBrief`：本次生成的不可变输入摘要；
- `GenerationPolicy`：课程范围、目标、深度、前置门禁、允许证据、固定题目蓝图和个性化策略；
- `StructuredResourceDraft`：讲义、实操指南、学生测验、教师答案四类结构化草稿；
- `ResourceAuditReport`：审核结论、问题清单和证据账本；
- `CandidateLearningPackage`：最终候选学习包。

状态含义已经拆开：

| 状态 | 含义 |
|---|---|
| `generation_status` | 四类资源是否都被正确解析生成 |
| `audit_status` | 内容、证据、题答关系、Notebook 等是否通过审核 |
| `publication_status` | 是否有资格进入发布候选；只能由系统计算 |

其中 `publication_status` 不由模型填写。当前 CNN 即使内容生成成功、审核通过，也必须因为前置门禁未解除而保持 `candidate_draft`。

### 2. 将“一个大 JSON”改为四次独立受控生成

当前生成过程改为四次独立模型调用：

1. 个性化讲义；
2. PyTorch 实操指南；
3. 学生分层测验；
4. 教师答案与诊断。

系统固定学生卷的 8 题蓝图：2 道概念题、2 道形状推理题、2 道代码理解/补全题、1 道调试题、1 道综合题。模型只能调节难度、提示和脚手架，不能修改题型、题号、知识范围或发布状态。

教师卷在学生卷生成后才调用模型，并把学生题号与题目作为冻结输入；教师答案只能与既有 `question_id` 对齐，不能增删或重写学生题目。

### 3. 建立 CNN 官方证据冻结机制

新增 CNN Demo 证据包工具，覆盖：

- PyTorch `torch.nn.Conv2d` 稳定文档；
- PyTorch Tensor 教程；
- 基于审核证据派生的练习。

每条证据保存来源 URL、最终解析 URL、抓取时间、页面文本哈希、片段文本与哈希、片段定位、许可状态、审核状态、审核人和审核时间。派生练习明确标为 `system_derived`，并记录其父证据编号，避免把系统设计的练习误写成官方原始材料。

证据状态分为 `candidate / reviewed / approved`：当前可用于候选 Demo 的是 `reviewed`；只有最终实际被技术结论引用的证据达到 `approved`，才可能进入 `release_candidate`。

### 4. 增加确定性审核与独立证据蕴含核验

当前审核会检查：

- 技术结论是否使用允许的证据编号；
- 结论是否超出课程知识范围或命中禁止主题；
- 证据片段是否支持当前结论；
- 学生卷是否泄漏答案；
- 学生题号与教师答案题号是否一一对应；
- 学生卷是否满足固定 8 题蓝图；
- Notebook 是否真正执行成功。

其中证据蕴含核验是独立的 `LLMClaimSupportVerifier`：它只接收“结论 + 已冻结的证据片段”，只能返回 `supported / unsupported / uncertain`，不能联网检索、不能补充事实、不能改写证据。`unsupported` 会直接导致审核失败；`uncertain` 或核验 API 异常会进入 `needs_review`。

### 5. 增加系统拥有的 PyTorch Notebook 执行验证

Notebook 的核心代码不由模型生成，而是由系统固定：构造输入张量、执行 `nn.Conv2d`、计算并断言输出 shape。执行过程有：

- 可配置超时，默认 30 秒；
- 独立临时工作目录；
- 输出上限；
- 固定必需单元格和 shape 断言；
- `network_dependency=forbidden`；
- 如运行环境不能真正强制断网，则明确标记为 `network_isolation=best_effort`。

这保证模型只能写教学解释和任务，不能让任意模型生成的 Python 代码进入执行环境。

### 6. 增加三画像控制变量评测

已支持三份画像对照：

- 基础补齐型：评测对照画像；
- 当前真实画像：评测基线；
- 基础巩固型：评测对照画像。

评测固定课程范围、目标、深度、证据、题型和 Notebook，只改变学习者画像。当前会从实际生成结果中计算：

- 前置复习段落数；
- 起始代码比例；
- 平均测验难度；
- 调试提示层数；
- 教师复习任务数；
- 讲解顺序；
- 反馈策略。

因此可以证明“个性化”不只是换一句措辞，而是会影响资源结构与教学策略。

### 7. 增加展示导出与模型可用性检查

已增加：

- `resource-model-check`：检查兼容 API 的连通性、鉴权、模型、JSON 输出模式、实际结构化模式、耗时与密钥安全状态；
- `resource-freeze-cnn-evidence`：抓取并冻结 CNN 官方证据；
- `resource-build-brief`：将上游画像、课程规划和领域检索交接结果转为不可变生成简报；
- `resource-generate`：生成候选学习包并导出展示目录。

展示目录会包含总览、四类资源、固定 Notebook、Notebook 执行报告、生成追溯、审核报告、证据账本、个性化报告、三画像对比报告与证据审核清单。总览页会醒目展示 `generation_status`、`audit_status`、`publication_status` 及当前发布阻塞原因。

资源命令也已从 Neo4j 图谱依赖中解耦：即使图谱服务未启动，资源生成相关命令仍可独立运行。

## 三、拉取时与现在的对比

| 维度 | 刚拉下仓库时 | 当前状态 |
|---|---|---|
| 资源生成 | 确定性样例/候选草稿为主 | 四类资源独立真实模型接口已就绪 |
| 模型权限 | 有资源生成契约，但未形成完整运行门禁 | 模型无课程、证据、审核、执行和发布权 |
| 输入利用 | 有画像、课程和证据基础对象 | 三类上游交接可组合成不可变生成策略 |
| 证据治理 | 候选块、引用和人工审核基础存在 | CNN 官方证据可冻结到页面/片段哈希并追溯 |
| 个性化 | 有适配契约 | 三画像控制变量评测与结构化指标已实现 |
| 学生/教师测验 | 基础资源验证 | 固定 8 题蓝图、学生卷/教师卷独立 Schema、题号强对齐 |
| Notebook | 没有实际 CNN 核心执行闭环 | 系统固定 PyTorch 核心代码、shape 断言、超时与报告 |
| 输出展示 | 候选资源与 JSON 报告 | 可直接给评委查看的完整候选学习包目录 |
| 发布安全 | 证据审核原则存在 | `candidate_draft / release_candidate` 由系统确定性计算 |

## 四、当前完成度与未完成事项

### 已完成（可以展示）

- 受控资源生成流程、四类材料结构、审核规则和状态机；
- CNN 官方证据冻结工具和证据审核清单；
- 模型兼容接口与能力检查命令；
- Notebook 核心执行器；
- 三画像对比指标与展示包导出；
- 资源模块自动测试与静态检查通过。

### 尚未完成（依赖本机环境或人工审核）

1. **真实 API 实跑**：本机目前未发现 `SKILLFORGE_LLM_BASE_URL`、`SKILLFORGE_LLM_API_KEY`、`SKILLFORGE_LLM_MODEL` 的有效配置，因此尚未调用真实模型生成最终内容。
2. **正式证据审核**：CNN 证据尚未由人工确认并标记为 `approved`，因此不具备正式发布资格。
3. **前置知识解除**：当前学习者的 `dl.vision.image-tensor` 前置知识未完成，系统必须维持 `candidate_draft`。
4. **本机 Notebook 环境修复**：当前机器的 PyTorch 导入受到 Windows 网络服务初始化错误影响，Notebook 执行器会如实报告失败，不会虚假标记为通过。
5. **依赖环境补齐**：项目要求 Python 3.12 与完整依赖环境；当前本机只有 Python 3.13，且缺少 `pydantic-settings`，因此 CLI 的真实运行环境尚需按项目依赖安装。

## 五、下一步建议

1. 使用 Python 3.12 创建项目环境并安装锁定依赖；
2. 在本机 `.env` 填入兼容 API 的地址、密钥和模型名（密钥不进入 Git）；
3. 执行 `resource-model-check`，先确认模型 JSON 输出能力；
4. 执行 `resource-freeze-cnn-evidence`，由人工填写审核人与许可证确认信息；
5. 使用现有三份上游 JSON 运行 `resource-build-brief`；
6. 执行 `resource-generate`，导出第一份真实模型 CNN 候选学习包；
7. 运行三画像评测，检查至少两个数值指标和一个结构类别是否产生可解释差异；
8. 展示时以总览页为入口，强调“内容可以生成，但前置门禁和证据门禁未解除，因此系统不会自动发布”。

## 六、汇报时可以直接这样概括

> 我负责的是资源生成 Agent 的受控生成部分。项目原来已经有课程图谱、知识库和学情适配基础，但资源生成主要是候选模板和契约验证。我现在把它补成了一个可接真实大模型的完整闭环：课程规划决定教什么，领域证据决定依据什么，学情画像决定怎么教，大模型只负责写讲义、实操、测验和教师诊断；系统再用证据核验、题答对齐、Notebook 实执行和发布门禁决定结果是否可信、是否可展示、是否可发布。当前 CNN 示例虽然可以生成候选学习包，但因为图像张量前置知识未完成、证据尚未正式批准，所以系统会明确标记为 candidate_draft，不允许自动发布。
