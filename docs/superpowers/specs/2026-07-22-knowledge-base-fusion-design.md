# 知识库分层融合设计

日期：2026-07-22
状态：待用户审核

## 1. 背景与决策

项目当前有两套队友产物：

- `知识库/`：包含原始 PDF、代码、来源清单和 1,423 条候选切片，来源信息较完整，但英文论文抽取、概念标注、许可记录和审核状态尚未达到发布标准；
- `processed/`：包含 710 条切片、BM25、FAISS 和 pickle 产物，部分论文文本抽取更好，但来源追溯缺失、切片尺寸失控、构建过程不可复现。

融合不采用文件拼接，也不把任何现有索引直接升级为正式索引。最终选择“分层融合”：保留两套原始产物，通过独立适配器进入统一候选层，完成来源核验、重新切片、去重、标注和审核后，再发布到现有证据服务。

## 2. 目标与非目标

### 2.1 目标

- 最大限度回收两位队友已经完成的来源搜集、文本抽取和工程资料整理工作；
- 建立一个可追溯、可审核、可重建的统一知识底座；
- 保持学习证据、智能体工程和项目资料之间的检索边界；
- 延续现有 `SourceRecord`、`Citation`、`EvidenceChunk` 和混合检索设计；
- 任何发布内容都能定位到权威来源或明确标注为团队派生资料。

### 2.2 非目标

- 不原样加载来源不明的 pickle；
- 不复用无法确认模型和版本的 FAISS 向量；
- 不把 `candidate` 数据自动提升为已审核数据；
- 不在本阶段实现智能体内部逻辑；
- 不将主题相近视为文本重复并直接删除。

## 3. 方案比较

### 3.1 方案 A：直接拼接

把两套 JSONL 合并，按文本哈希去重，然后继续使用现有索引。

优点是速度快。缺点是会保留错误概念、英文粘连、超大切片和缺失引用，也无法解释旧向量的模型来源。该方案不满足证据服务要求，淘汰。

### 3.2 方案 B：完全重建

只保留原始 PDF 和代码，丢弃全部现有切片与索引，从零重新抽取。

优点是数据最整洁。缺点是浪费第二套中质量较好的英文抽取和团队工程笔记，也不能体现队友已经完成的工作。该方案作为严重异常来源的回退路径，不作为主路线。

### 3.3 方案 C：分层融合

保留两套产物作为只读输入，分别转换为带来源等级、语料域和拒绝原因的候选记录。相同原始来源只选择一条权威发布链，其他版本作为抽取对照保存。所有正式索引统一重建。

该方案兼顾质量、工作复用和可解释性，确定为实施路线。

## 4. 融合架构

融合流程分为五层：

1. **只读原始层**：冻结 `知识库/` 和 `processed/`，记录文件清单、大小和 SHA-256，不在原目录内生成中间产物；
2. **来源登记层**：为每个原始来源建立唯一 `SourceRecord`，记录规范 URL、版本、获取时间、许可状态和所属语料域；
3. **候选转换层**：两个适配器把现有 JSONL 转为统一候选记录，同时保留原始行号、原始字段和拒绝原因；
4. **治理审核层**：执行文本质量、引用、许可、切片尺寸、概念标注、重复和语言检查，只有通过人工审核的记录才能发布；
5. **发布检索层**：PostgreSQL 保存规范来源与全文，Qdrant 保存重新生成的稠密/稀疏向量，Neo4j 只保存已审核概念关系。

### 4.1 语料域

来源登记时必须归入一个域：

- `learning_evidence`：机器学习、深度学习、LLM、RAG、LoRA 等教学证据；
- `agent_engineering`：LangChain、LangGraph、FAISS、Neo4j、部署和检索工程资料；
- `project_material`：比赛方案、项目手册、团队总结和案例文档。

默认查询只检索 `learning_evidence`。智能体搭建阶段可显式检索 `agent_engineering`。`project_material` 只用于项目规划和内部参考，不参与教学答案生成。

语料域存储在来源记录中，并作为 Qdrant payload 的过滤字段。检索结果仍返回统一的 `EvidencePackage`。

实现时为 `SourceRecord` 增加必填 `corpus_id`，并在 PostgreSQL 来源表中单独建列。`EvidenceChunk` 通过 `source_id` 继承语料域，发布到 Qdrant 时把 `corpus_id` 冗余写入 payload，以便在向量召回阶段完成过滤。

## 5. 两套数据的融合规则

### 5.1 `知识库/`

- 原始 PDF 和代码作为主要来源资产保留；
- 现有来源 ID、URL、路径、页码或行号优先复用；
- 中文 PDF 和代码切片进入候选层，但必须补齐 `Citation`、规范哈希和审核字段；
- 所有英文论文从原始 PDF 重新抽取，现有粘连文本不进入正式索引；
- 自动生成的 `concept_ids`、`content_kind` 和难度只作为建议，不作为审核结果；
- `arXiv` 不视为许可证，必须记录具体许可 URL或保持 `pending`/`metadata_only`；
- MIT 仓库中的 PDF 与代码分别核验，避免用仓库许可证替代第三方文档许可。

### 5.2 `processed/`

- 只读取 `index_chunks.jsonl`；pickle 不反序列化，旧 FAISS/BM25 仅保留为审计样本；
- LoRA、RAG、GraphRAG、QLoRA 等论文文本可用于比较抽取质量，但必须先重新绑定原始 PDF、规范 URL和页码；
- 大于目标上限的论文块重新按标题、段落和页码切分，不能直接截断；
- 少于 20 字、纯标题、纯命令标签和重复块默认拒绝或与相邻内容合并；
- LangChain、部署、FAISS、Neo4j 等资料进入 `agent_engineering`；
- 实训手册和团队总结进入 `project_material`，只有能绑定外部权威来源的知识段落才可派生为 `learning_evidence`；
- 没有稳定 HTTP(S) 地址的团队资料只保留为 `reference_only`；只有取得稳定内部文档 URL 和明确授权后，才能生成满足现有 `Citation` 契约的发布切片；
- `token_count` 使用固定版本的 `intfloat/multilingual-e5-large` tokenizer 重新计算，不再使用字符数替代 token 数。

## 6. 来源身份、版本和去重

去重按三个层次处理：

1. **来源级身份**：优先使用 DOI、arXiv ID、规范 URL或仓库 URL 加提交版本识别同一来源；
2. **版本级身份**：相同论文的不同 PDF 或抽取结果共享来源身份，但保留不同 `version_label` 和文件哈希；
3. **切片级重复**：使用项目的 NFKC 标准化哈希识别精确重复，用 5-gram Jaccard 识别近重复。

同一来源存在两种抽取时，不拼接两套切片。系统基于空格保留、页码可定位、字符异常率和结构完整性选择主抽取版本，另一版本只作对照。不同权威来源即使语义相近也不删除，而是保留各自引用并建立概念关联。

## 7. 统一数据流

每次融合构建执行以下固定顺序：

1. 生成只读输入清单和哈希；
2. 建立或更新来源登记表；
3. 根据规则分配语料域和来源等级；
4. 运行两个输入适配器，生成候选记录和转换报告；
5. 对需要修复的来源重新抽取和切片；
6. 补齐引用、规范哈希、语言、概念、内容类型和难度；
7. 执行自动质量门禁并输出逐条拒绝原因；
8. 进行人工审核，发布通过记录；
9. 从 PostgreSQL 的已发布记录重建 Qdrant 和 Neo4j；
10. 运行固定评测集并生成版本化融合报告。

构建必须幂等。相同输入和配置重复运行时，规范记录、哈希和发布索引应保持一致。

## 8. 质量门禁与异常处理

候选记录出现下列任一问题时不得发布：

- 来源未登记或无法定位；
- `allowed` 状态缺少许可 URL；
- 缺少 `Citation.url` 或有效页码/行号；
- 文本少于 20 字、超过 900 个模型 token 或存在严重英文粘连；
- 规范哈希不匹配；
- 概念为空、明显误标或内容类型不可信；
- 未通过人工审核；
- 与已发布内容构成未解释的重复。

转换失败不终止整个批次。系统生成机器可读报告，至少包含输入文件、行号、来源 ID、处理结果、拒绝代码和说明。未知字段和原始行必须保留，避免静默丢失队友数据。

## 9. 索引发布策略

- PostgreSQL 是唯一事实来源；
- Qdrant 向量必须记录 embedding 模型、版本、维度、归一化方式和构建版本；
- 稠密和稀疏索引只能接收 `reviewed=true` 的发布切片；
- Qdrant payload 增加语料域，用于查询过滤；
- Neo4j 只接收已审核概念和来源关系，自动误标不能生成正式边；
- 每次模型、切片规则或规范文本变化都生成新索引版本，不原地混用旧向量；
- 旧 pickle 和 FAISS 文件不进入运行时依赖。

## 10. 测试与验收

### 10.1 测试范围

- 两个适配器的字段映射和拒绝原因单元测试；
- 结构优先切片测试：目标范围为 250–700 个模型 token、重叠 80 个 token、硬上限 900 个 token，标题、代码块和公式不得被无条件截断；
- 来源身份、版本选择、精确重复和近重复测试；
- 英文粘连、超大块、短块、许可和引用门禁测试；
- PostgreSQL 发布与 Qdrant/Neo4j 重建的集成测试；
- 语料域过滤测试，确保学习查询不会默认召回部署或项目手册；
- 固定输入重复构建的幂等测试；
- 中英文黄金查询集的回归评测。

### 10.2 融合验收条件

- 两套输入的每一行都有 `accepted`、`rejected`、`superseded` 或 `reference_only` 结果；
- 所有已发布切片都能通过现有 Pydantic 领域模型和治理策略；
- 已发布切片缺失引用数为 0，未审核入索引数为 0；
- 已知英文粘连和超大论文块进入正式索引的数量为 0；
- 所有索引都能由版本化配置从 PostgreSQL 重建；
- 未解释重复率低于 2%，引用重新定位成功率不低于 98%；
- 延续项目目标：Recall@5 不低于 0.85、MRR@10 不低于 0.75、nDCG@10 不低于 0.80；
- 中文与英文召回差距不超过 0.05，本地 P95 检索延迟低于 2 秒。

## 11. 分阶段落地

### 阶段 1：清单与试运行

冻结输入，建立来源登记和两个适配器，对全部 2,133 条现有记录生成干跑报告，不发布索引。

### 阶段 2：第一批可信融合

优先处理 `知识库/` 中中文教学 PDF 和代码，补齐引用、许可与审核，形成第一批可发布证据。

### 阶段 3：英文论文修复

重新抽取 12 篇英文论文，利用 `processed/` 中较好的论文文本做对照，完成来源级版本选择和重新切片。

### 阶段 4：工程与项目资料分域

整理 LangChain、FAISS、Neo4j、部署和项目手册，分别进入 `agent_engineering` 与 `project_material`，不污染默认教学检索。

### 阶段 5：统一发布与评测

从已审核记录重建 PostgreSQL、Qdrant 和 Neo4j 发布面，运行评测集并冻结首个融合版本。

## 12. 预期结果

融合完成后，两位队友的成果都被保留但承担不同角色：第一套提供来源和证据主干，第二套提供英文抽取对照、工程知识和项目材料。正式系统只消费经过统一治理后发布的记录，因此能够复用已有工作，同时避免把现有质量问题固化进后续智能体。
